On October 19 the scheduled run creation/start times were 13:17:03Z (9:17 AM Eastern), 19:54:12Z (3:54 PM), and 23:38:29Z (7:38 PM). On October 20 the next runs were 04:47:13Z and 10:01:58Z. These are multi-hour gaps in run creation, not evidence of publishing API failures. For the 19:54 run, the dispatch job started at 19:54:18Z and completed successfully at 19:54:46Z.

Evidence: [3:54 PM run](https://github.com/ASME-OSU/ASME-Social-Hub/actions/runs/39314821564), [7:38 PM run](https://github.com/ASME-OSU/ASME-Social-Hub/actions/runs/39342817368), [workflow history](https://github.com/ASME-OSU/ASME-Social-Hub/actions/workflows/dispatch.yml).

GitHub documents that scheduled events can be delayed or dropped under load, and that concurrency groups can replace a pending run. The observed timestamps support a schedule-delivery problem; they do not establish GitHub's internal cause for every missing hourly opportunity. See [scheduled workflow troubleshooting](https://docs.github.com/en/actions/how-tos/troubleshoot-workflows) and [concurrency](https://docs.github.com/en/actions/concepts/workflows-and-actions/concurrency).

## Changes

- Schedule dispatch at minutes 7 and 37, retaining the shared repository concurrency group and durable publishing-intent checkpoints. Increasing opportunities reduces normal wait times but does not provide a delivery guarantee.
- Write `data/dispatcher-health.json` only from live dispatches that finish campaign processing and archive preparation. `lastSuccessfulLiveRunAt` advances only when no publishing action failed, including successful no-op executions. `lastLiveRunAt` and `lastLiveRunStatus` also identify completed executions with publishing failures. A thrown error leaves the previous success intact. Preview does not write health or campaign state.
- The normal build copies health into Pages. The dashboard refreshes every minute without browser caching; when connected it reads health directly from the selected repository branch. Missing, invalid, future-dated, inaccessible, or never-recorded health is shown as unknown. After 90 minutes without a successful completion, the dashboard shows a neutral scheduling-delay status with the age of the last success. It says posts may be late and does not claim a run is queued. More than 12 hours triggers an actionable stale warning; a recorded publishing failure appears immediately. The 12-hour threshold exceeds the largest recent observed gap (9 hours 8 minutes), while retaining a warning before the 24-hour catch-up window closes. These are in-dashboard states, not out-of-band notifications. A fresh successful completion clears them.
- Dashboard Preview and Run live controls call the same dispatch workflow, with explicit boolean inputs. Live requires an affirmative confirmation and publishes all due campaigns. Use a main-branch connection and a token with **Actions write** permission in addition to existing Contents permission. Requests are disabled while submitting. Review the linked Actions run list for completion; requesting a run does not mark the dispatcher healthy.
- Editor conflict checks compare canonical event content. Only revision, status, results, log, and generated flyers are excluded. Changed content blocks saving even if revision was not incremented. Saves start from the newest record, preserve publishing receipts, increment revision, and use GitHub's latest file SHA. A concurrent change after reading still causes GitHub to reject the save; reload rather than silently retrying.
- Future schedule edits reopen only explicit missed-window skips without attempts, containers, or delivered results. Legacy Instagram skips are recognized only with an exact last channel log of `Publishing window missed`. Disabled, unrelated, ambiguous, and completed states remain protected. Legacy skips with no identifiable reason require officer review.

## Deployment and limitations

These changes remain local on `codex/dispatcher-reliability`; they have not been pushed, merged, deployed, or used to publish announcements. Existing local work was preserved. No campaign records should be reset to demonstrate the fix.

After review, the schedule changes must reach the repository's default branch for automatic scheduling. The first completed successful live dispatch creates the health file; before that the dashboard intentionally reports unknown. A successful script timestamp confirms dispatcher execution, not that every integration credential is valid when there were no due campaigns, nor that subsequent persistence or Pages deployment succeeded.

If precise delivery remains a requirement, configure an independent scheduler to invoke the existing `dispatch.yml` workflow every 30 minutes through GitHub's `workflow_dispatch` API with `ref: main` and `inputs: {dry_run: false}`. Keep its credential in the scheduler's secret store, scoped to this repository with Actions write access. Do not publish directly from the external scheduler: all invocations must retain repository serialization and durable write-intent protections. Runner availability and workflow failures can still delay publishing. No external scheduler was provisioned as part of this change; choosing and configuring that service remains necessary for an independent trigger.

Validation uses temporary campaign fixtures, injected publishing services, and mocked browser GitHub calls. No test announcements are sent and no production campaign records are changed.

## Campaign controls and previews

Campaign details now include **Delete campaign**, with explicit confirmation and repository connection required. Deletion writes a cancelled record with `deletedAt` using the latest GitHub SHA, then removes the campaign from the dashboard and archive. It retains publishing receipts, attempts, and logs as a deletion record so a stale run cannot recreate or resend previously delivered content. Existing native GroupMe events still follow cancellation cleanup; published Instagram posts and GroupMe bot messages are not removed. Concurrent content edits and rejected SHA writes leave the campaign visible for review.

Posting-date warnings appear in the editor, campaign cards, and details. They explain when a publishing window has closed and the channel will not post, or when a late post remains eligible within the dispatcher's 24-hour catch-up window. Disabled and delivered channels are excluded. Explicit skipped states require a future posting time to reopen.

Feed previews now use an Instagram-style layout in the editor and campaign details: account header, post artwork, carousel navigation, familiar action icons, and a caption region that scrolls by pointer or keyboard. The editor uses the exact caption function used by the publisher, including advertising details. Published campaign previews use their recorded caption and media. Story previews and exported artwork retain their original rendering; the Instagram interface is only part of the browser preview.

GroupMe previews now show Gearley's bot avatar and an announcement bubble in the editor and campaign details. Preview text shares the dispatcher's message formatter, including the 1,000-character validation. Enabled announcements over that limit are rejected before the campaign is committed, including after flyer uploads finalize their URLs. New-upload previews explain that links finalize on save; recorded attempts and delivered announcements retain their original message text. The avatar is the user-supplied `Cute Red-White Robot Mascot Head.png`, copied unchanged to `docs/assets/logos/groupme-bot.png`. Bot display name and preview avatar are configured under `integrations.groupme`; these settings do not alter the remote bot account or send a message.

### Optional authenticated scheduler entrypoint

The user selected the GitHub fallback for now; **no external scheduler is provisioned**. A future scheduler can use the existing `workflow_dispatch` interface described above, or the new `repository_dispatch` event type `campaign-dispatch`. The latter previews by default and publishes only when the caller sets `client_payload.mode` to `live`. It invokes the same serialized reusable workflow on `main`, with no payload-controlled shell command or checkout ref. The workflow change must reach the default branch before this event can trigger it.

For a future independent scheduler, send an authenticated `POST` to `https://api.github.com/repos/ASME-OSU/ASME-Social-Hub/dispatches` with `Accept: application/vnd.github+json` and the following JSON for a safe preview:

```json
{"event_type":"campaign-dispatch","client_payload":{"mode":"preview"}}
```

After verifying preview results, an explicitly configured publishing schedule would use `"mode":"live"`. Keep credentials in that scheduler's secret store. GitHub requires repository **Contents: write** for this repository-dispatch endpoint; the existing workflow-dispatch endpoint instead requires **Actions: write**. A successful API response acknowledges the trigger, not publication or workflow completion. Follow the returned run history and persisted health. See GitHub's [repository-dispatch API permissions](https://docs.github.com/en/rest/repos/repos#create-a-repository-dispatch-event) and [default-branch event behavior](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#repository_dispatch).

## Additional GitHub-only recovery

The primary dispatch schedule remains every 30 minutes at minutes 7 and 37, with the scheduled Insights catch-up at minute 19. A lightweight **Dispatcher watchdog** now checks at minute 49 and after successful main-branch dashboard renders caused by pushes or Calendar jobs caused by schedules. These completion events add recovery opportunities that do not require another cron event to arrive. Manual render, Calendar, and Insights operations do not activate this completion fallback. The watchdog does not follow dispatcher completions, so it cannot form a dispatch loop.

The watchdog reads the committed health file directly from `main`. If the last successful live dispatch is less than 30 minutes old, it stops after that read. Otherwise it checks recent dispatcher and Insights runs. It requests the existing dispatcher only if no dispatcher or scheduled Insights run is queued, waiting, or running, and no dispatcher request was created in the preceding 30 minutes. Missing health can recover; inaccessible or malformed API responses fail the check without requesting a job. Manual watchdog requests default to preview. Its job receives only Contents read and Actions write through the built-in workflow token; it has no Instagram or GroupMe credentials, does no npm install, and builds or deploys no artwork. Any requested live work still goes through the same serialized dispatcher and publication-intent safeguards. GitHub explicitly allows [workflow-dispatch requests made with `GITHUB_TOKEN`](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/trigger-a-workflow#triggering-a-workflow-from-a-workflow) to start runs, so no external service or new credential is required.

All participants in the shared `campaign-repository` concurrency group now set `queue: max` with `cancel-in-progress: false`. This retains up to 100 waiting jobs rather than replacing the single pending job when another task arrives. Checkout still resolves `main` after the job obtains the shared lock; dispatch does not reuse the old trigger commit or force-push over campaign edits. This closes a documented queue-replacement risk; the observed multi-hour gaps were in creation times and are not evidence that this queue risk caused those gaps. See GitHub's [concurrency queue documentation](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#concurrency).

These changes improve recovery within GitHub and avoid running another full publisher on every watchdog check. They cannot promise an exact posting time: GitHub can delay or drop all scheduled triggers, runner capacity can be unavailable, and API requests can fail. A watchdog run that never starts cannot detect its own absence. The dashboard's recorded health remains the evidence of actual dispatcher execution; requesting recovery is not itself a successful heartbeat.

Manual **Insights** now defaults to `analytics_only: true`. This collects eligible metrics, persists them, and deploys the updated dashboard while suppressing dispatcher, expiry-check, and alert-message steps. It provides an explicit path for recovering a missing statistics snapshot without creating posts or officer alerts. Scheduled Insights retains its normal dispatch catch-up and alert behavior.

Regression coverage includes fresh and missing heartbeats, stale recovery, pending/running dispatch suppression, recent-request throttling, failure-response redaction, default preview behavior, trusted main-branch completion guards, the absence of dispatch-trigger loops, and analytics-only publishing/alert suppression. All test requests are mocked; no live dispatcher, social post, or alert was sent during validation.
